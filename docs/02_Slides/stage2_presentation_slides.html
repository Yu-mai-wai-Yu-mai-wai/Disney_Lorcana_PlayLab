03. Architectural Evolution

วิวัฒนาการสถาปัตยกรรม: จาก S3 สู่ Full IaaS

การตัดสินใจเชิงวิศวกรรม (Architectural Decision) เพื่อตอบโจทย์เกณฑ์การประเมินวิชา Cloud Computing

❌ สถาปัตยกรรมเดิม: Pure S3 Static Hosting

ช่วงแรกระบบโฮสต์ Frontend บน S3 Bucket Static Web แม้จะราคาถูกและทนทานสูง แต่มีข้อจำกัดร้ายแรงในเชิงการประเมินวิชาการ:

  • !
    S3 ไม่มี Compute Engine ไม่สามารถรัน Container หรือ Node.js Server ได้
  • !
    ไม่ได้แสดงทักษะ Core IaaS: Custom VPC, Subnet CIDR, Security Group Layering
  • !
    ขาดการพิสูจน์เรื่อง Auto Scaling และ Elasticity ในการสอบวิชา Cloud
✅ สถาปัตยกรรมปัจจุบัน: Lean Multi-AZ IaaS Stack

ยกระดับสู่สถาปัตยกรรม Dual-Mode สมบูรณ์แบบ (IaaS Primary + Serverless Fallback) ตอบโจทย์ครบทุกเสาหลัก Well-Architected:

  • ✓
    Multi-AZ VPC: กระจาย Subnet ข้าม us-east-1a และ us-east-1b
  • ✓
    Application Load Balancer (ALB): กระจายโหลดและทำ Health Check /health
  • ✓
    EC2 Auto Scaling Group: สเกล 1 ถึง 3 เครื่องตาม CPU > 60%
  • ✓
    Docker Multi-stage: รัน Nginx + Node.js บน Alpine Linux ใช้แรม < 150MB

💡 ความฉลาดของ "Zero NAT Gateway"

ในองค์กรทั่วไป มักวาง EC2 ใน Private Subnet แล้วต่อผ่าน NAT Gateway ซึ่งมีค่าใช้จ่าย ~$32.40 ต่อเดือน ซึ่งจะกลืนงบ $50 ใน Learner Lab หมดภายใน 1 เดือนครึ่ง!

🔒 Chained Security Groups Hardening

เราเลือกใช้ Public Subnet คู่กับ Chained Security Groups:
• lorcana-alb-sg รับ HTTP Port 80 จากภายนอก
• lorcana-ec2-sg บล็อกการเข้าถึงตรงจากอินเทอร์เน็ตทั้งหมด ยอมรับ Port 80 และ 3001 เฉพาะทราฟฟิกที่ส่งต่อมาจาก ALB SG เท่านั้น! ปลอดภัยเทียบเท่า Private Subnet ในราคา $0.00

05. Elastic Compute & Load Balancing

Application Load Balancer & Auto Scaling

การกระจายทราฟฟิก, Health Check แบบอัตโนมัติ และการสเกลตามภาระงานจริง (Elasticity)

⚖️ Application Load Balancer

• ชนิด Internet-Facing กระจายข้าม 2 AZs
• จุดเข้าใช้งานหลักผ่าน DNS Name ของ AWS
• Health Check: GET /health ทุก 15 วิ
• ถอด Instance ที่ไม่สมบูรณ์ออกจากระบบทันที

HEALTHY 200 OK
📜 Launch Template (Amazon Linux 2023)

• Instance Type: t3.micro (2 vCPU, 1GB RAM)
• แนบ IAM LabInstanceProfile อัตโนมัติ
• ใช้ IMDSv2 ป้องกัน SSRF Token Theft
• User Data Script ติดตั้ง Nginx & ดึงโค้ดขึ้นรันอัตโนมัติภายใน 90 วินาที

📈 Auto Scaling Group Policy

• Capacity Bounds: Min 1, Max 3, Desired 1
• Target Tracking Metric: CloudWatch ASGAverageCPUUtilization
• Threshold: CPU > 60% สปอว์นเครื่องที่ 2 และ 3 ทันที
• Scale-In: ยุบเครื่องคืนอัตโนมัติเมื่อโหลดลดลง

🔬 การยืนยันผลการทดลอง: ใช้สคริปต์ .\scripts\stress_test.ps1 -TotalRequests 2000 -Concurrency 20 ยิงจำลองโหลดผู้เล่น 2,000 requests พบว่า CloudWatch Target Tracking Alarm เปลี่ยนสถานะเป็น In alarm และ ASG สปอว์น EC2 Instance เครื่องที่ 2 ขึ้นมาช่วยรับโหลดได้จริง 100%

06. Containerization & Web Server

Multi-stage Docker & Nginx Reverse Proxy

การรีดประสิทธิภาพให้ทำงานบน Instance ขนาดเล็ก (t3.micro 1GB RAM) โดยไม่มี Out-of-Memory

🐳 Multi-stage Docker Architecture

เพื่อไม่ให้ Image บวมบน EC2 เราแยกกระบวนการ Build ออกจาก Production Runtime อย่างเด็ดขาด:

  • 1
    Build Stage: ใช้ Node.js 20 Alpine รัน npm run build คอมไพล์ Vite React 19 SPA และ TypeScript backend
  • 2
    Production Stage: คัดลอกเฉพาะโฟลเดอร์ dist/ มาใส่ใน Nginx Alpine และ Node.js Runtime
  • 3
    Lightweight Footprint: Image รวมมีขนาด < 100MB และใช้ RAM เฉลี่ยเพียง ~120MB - 150MB ปลอดภัยจากการชนขีดจำกัด 1GB ของ t3.micro
⚡ Nginx Reverse Proxy Flow

Nginx ทำหน้าที่เป็น Front Door ประจำแต่ละ EC2 Instance:

Path Pattern Target Upstream หน้าที่การทำงาน
/ (Root) Static HTML/JS เสิร์ฟ React 19 SPA พร้อม Gzip Compression
/api/* Node.js :3001 REST API สำหรับ Auth, Decks, และ Dataset
/ws Node.js :3001 WebSocket Upgrade สำหรับซิงค์กระดาน 2 ฝั่ง
/health Nginx direct 200 ตอบ ALB Health Check ทันทีโดยไม่กวน App loop

07. Real-Time Engine & State Sync

Real-Time WebSockets Engine (v1.5.0)

การจัดการสถานะห้องเล่น 2 ผู้เล่น, การซิงค์พิกัดการ์ด และระบบจัดการข้อผิดพลาดทางเครือข่าย

⚡ Sub-100ms Action Sync

ส่งผ่าน Event โครงสร้าง JSON ที่กระชับ:
• JOIN_ROOM เข้าห้อง 6 หลัก
• CARD_MOVED ลากการ์ดลง Play Area
• CARD_EXERTED แตะการ์ดเอียง 90°
• LORE_UPDATED ซิงค์แต้ม Lore 0-20
• TURN_PASSED สลับเทิร์นผู้เล่น

⏱️ 60s Rejoin Grace Period

หากผู้เล่นประสบปัญหาเน็ตหลุด (Network Disconnect) ระบบจะ ยังไม่ลบห้องทันที แต่จะให้เวลา 60 วินาทีพร้อมแจ้งเตือนคู่ต่อสู้ หากผู้เล่นรีเฟรชหรือต่อเน็ตติด ระบบจะ Re-hydrate สถานะเดิมบนกระดานให้เล่นต่อได้ทันที

🚪 Voluntary Exit Match

แยกแยะอย่างชัดเจนระหว่างเน็ตหลุดกับการ "กดยอมแพ้/ออกจากห้อง":
เมื่อผู้เล่นกดปุ่ม Exit Match จะส่ง LEAVE_ROOM ทันที เพื่อ Hard-delete คืนสล็อตห้องบน DynamoDB และแจ้งให้อีกฝ่ายทราบ ไม่ต้องรอ Grace Period 60 วินาทีให้เสียเวลา

🛡️ Optimistic Update with Authoritative Reversion

บนหน้าจอฝั่งตนเอง UI จะขยับการ์ดทันที (0ms Latency) พร้อมส่ง Event ออกไปทาง WebSocket หาก Backend พบว่าผิดกฎ (เช่น Ink ไม่พอ หรือการ์ดไม่ได้อยู่ในสถานะ Ready) จะส่ง Action ย้อนกลับมาให้เด้งการ์ดกลับจุดเดิม

🟢 1. เมื่อต้องการเปิดเดโม
.\scripts\lab_start.ps1

สั่งปรับ Desired Capacity = 1 บน ASG เพื่อเปิดเครื่อง EC2 ขึ้นมารับทราฟฟิกและเดโมให้อาจารย์ดูได้ภายใน 90 วินาที (~$0.033/ชั่วโมง)

🟡 2. เมื่อเลิกใช้งาน (Scale-to-Zero)
.\scripts\lab_stop.ps1

สั่งปรับ Desired Capacity = 0 และ Min Size = 0 เพื่อ Terminate EC2 ทุกเครื่อง ค่าใช้จ่าย Compute ลดลงเหลือ $0.0000/ชั่วโมง ทันที

🔴 3. เมื่อส่งจบโปรเจกต์
python .\scripts\lab_destroy.py

สคริปต์ล้างบาง ลบ ALB, Target Group, ASG, Launch Template, Security Groups และ VPC ทั้งหมด ค่าใช้จ่ายคลาวด์ตัดเหลือ 0% สมบูรณ์

13. Defense & Technical Q&A

แนวทางการตอบคำถามอาจารย์ (Defense Preparation)

การเตรียมความพร้อมทางวิชาการและเหตุผลเชิงสถาปัตยกรรม (Architectural Justification)

❓ ทำไมไม่ใช้ NAT Gateway?

คำตอบ: NAT Gateway มีค่าใช้จ่ายคงที่ ~$32.40/เดือน ซึ่งจะเผางบ $50 ของ Learner Lab หมดอย่างรวดเร็ว เราจึงออกแบบเป็น Lean VPC โดยวางใน Public Subnet แต่ใช้ Chained Security Groups ปิดกั้น Inbound ทั้งหมดให้เข้าได้เฉพาะจาก ALB SG เท่านั้น ซึ่งได้ความปลอดภัยระดับเดียวกันโดยต้นทุนเป็น $0.00

❓ ทำไมต้องทำ Multi-AZ?

คำตอบ: เพื่อบรรลุเสาหลัก Reliability & High Availability ตาม AWS Well-Architected Framework การกระจาย Subnet ข้าม us-east-1a และ 1b ช่วยป้องกัน Single Point of Failure (SPOF) หาก Data Center ฝั่งหนึ่งมีปัญหา ALB จะเบี่ยงทราฟฟิกไปเครื่องที่รอดชีวิตในอีก AZ ได้ทันที

❓ สเกลเครื่องแล้ว WebSocket หลุดไหม?

คำตอบ: สถาปัตยกรรมเรารองรับ 2 ทาง: ในระดับ IaaS เราเปิด Sticky Sessions บน Target Group เพื่อผูก Client ไว้กับเครื่องเดิม และในระดับสเตท เราเก็บข้อมูลห้องไว้บน Amazon DynamoDB ทำให้ถึงแม้จะต่อใหม่ หรือ Rejoin ก็ดึงสเตทเดิมมาเล่นต่อได้โดยไม่สูญหาย
