# คู่มือการทำงานของระบบ Disney Lorcana PlayLab Cloud

เอกสารฉบับนี้อธิบายภาพรวมการทำงานของ Disney Lorcana PlayLab Cloud แผนภาพสถาปัตยกรรม เส้นทางการไหลของข้อมูล การเปรียบเทียบการทำงานของระบบคลาวด์กับสิ่งของในชีวิตประจำวัน ขั้นตอนการสาธิตระบบ และอภิธานศัพท์เทคนิค สำหรับผู้สนใจและผู้ประเมินระบบ

---

## 1. ระบบนี้คืออะไร

Disney Lorcana PlayLab Cloud เป็นเว็บแอปพลิเคชันสำหรับเล่นการ์ดเกม Disney Lorcana แบบออนไลน์ผ่านเบราว์เซอร์ พร้อมระบบสนับสนุนการแข่งขันครบวงจร ประกอบด้วย:

1. **ระบบสร้างและจัดเด็คการ์ด:** ค้นหาการ์ดจากฐานข้อมูลการ์ดทางการจำนวน 3,242 ใบ (Set 1 ถึง Set 13) และจัดเด็คขนาด 60 ใบ
2. **ระบบวิเคราะห์เด็คอัตโนมัติ:** วิเคราะห์การกระจายตัวของค่าร่าย สัดส่วนการ์ดที่เปลี่ยนเป็นหมึกได้ สัดส่วนประเภทการ์ด และคะแนนความสอดคล้องของการ์ดในเด็ค
3. **ระบบห้องเล่นออนไลน์แบบเรียลไทม์:** สร้างห้องด้วยรหัส 6 หลักและเชื่อมต่อผู้เล่นสองคนเข้าด้วยกันผ่านระบบสองทางแบบทันที
4. **ระบบประมวลผลกฎกติกาการเล่น:** ตัวขับเคลื่อนกฎกติกาที่ทำงานตาม Comprehensive Rules ครอบคลุมขั้นตอนเทิร์น คีย์เวิร์ดทางการ 14 ชนิด และความสามารถของการ์ด
5. **ระบบบันทึกประวัติการแข่งขันและตารางผู้นำ:** บันทึกผลการแข่งขันแบบแยกส่วนประมวลผล และแสดงรายชื่อผู้เล่นที่มีสถิติชนะสูงสุดผ่านระบบหน่วยความจำแคชความเร็วสูง

### 2.2 เส้นทางการไหลของข้อมูลในแต่ละกิจกรรม

#### เส้นทางที่ 1: การลงทะเบียนและการเข้าสู่ระบบ
1. ผู้ใช้กรอกชื่อผู้ใช้และรหัสผ่านในหน้าเว็บ
2. เบราว์เซอร์ส่งคำขอไปยัง Application Load Balancer ซึ่งส่งต่อไปยังเซิร์ฟเวอร์ EC2 เครื่องใดเครื่องหนึ่ง
3. Nginx ทำหน้าที่พร็อกซีคำขอเข้าสู่ Node.js
4. เซิร์ฟเวอร์เข้ารหัสผ่านด้วยฟังก์ชันทางเดียวที่ปลอดภัยและตรวจสอบกับฐานข้อมูล DynamoDB ตาราง Users
5. หากข้อมูลถูกต้อง เซิร์ฟเวอร์จะออกโทเคนยืนยันตัวตนส่งกลับไปยังเบราว์เซอร์เพื่อใช้ในการติดต่อครั้งถัดไป

#### เส้นทางที่ 2: การสร้างเด็คและการวิเคราะห์ประสิทธิภาพ
1. ผู้ใช้เลือกการ์ดในหน้าจัดเด็คและกดบันทึก
2. เซิร์ฟเวอร์ EC2 บันทึกรายการการ์ดลงในตาราง Decks ของ DynamoDB
3. ในเวลาเดียวกัน เซิร์ฟเวอร์จะส่งข้อความรายการการ์ดเข้าสู่คิว Amazon SQS
4. AWS Lambda สำหรับวิเคราะห์เด็คจะดึงข้อความจากคิวมาประมวลผลคำนวณกราฟค่าร่ายและคะแนนการ์ด
5. เมื่อคำนวณเสร็จ Lambda จะบันทึกผลการวิเคราะห์กลับเข้าตาราง Decks ใน DynamoDB ทันที
6. หากข้อความในคิวเกิดความเสียหายหรือไม่สามารถอ่านได้ ระบบจะลองประมวลผลซ้ำ 3 ครั้ง หากยังล้มเหลว ข้อความจะถูกย้ายไปยังคิวข้อความตกค้าง (DLQ) โดยอัตโนมัติ

#### เส้นทางที่ 3: การเล่นเกมออนไลน์สองคน
1. ผู้เล่นคนที่หนึ่งสร้างห้องและได้รับรหัสห้อง 6 หลัก
2. เบราว์เซอร์เชื่อมต่อผ่านช่องทางสื่อสารสองทางแบบ WebSocket ไปยัง Amazon API Gateway
3. API Gateway เรียกใช้งาน AWS Lambda เพื่อบันทึกข้อมูลห้องลงใน DynamoDB
4. ผู้เล่นคนที่สองกรอกรหัส 6 หลักเพื่อเข้าร่วมห้องเดียวกัน
5. ข้อมูลการเล่น เช่น การลงการ์ด การโจมตี หรือการสะสมแต้ม จะถูกส่งผ่านช่องทาง WebSocket ไปยังคู่แข่งทันที โดยมีตัวขับเคลื่อนกฎกติกาคอยตรวจสอบความถูกต้องของการกระทำ

#### เส้นทางที่ 4: การสรุปผลการแข่งขันและการกระจายข้อมูล
1. เมื่อผู้เล่นคนใดคนหนึ่งสะสมแต้มครบ 20 แต้ม หรือคู่แข่งการ์ดหมดกองตอนจบเทิร์น เกมจะตัดสินผู้ชนะ
2. เบราว์เซอร์ส่งผลการแข่งขันไปยังเซิร์ฟเวอร์ EC2 ผ่านคำสั่งที่มีโทเคนยืนยันตัวตน
3. EC2 ตรวจสอบว่าผู้ส่งคำขอเป็นผู้เล่นในแมตช์จริง จากนั้นส่งข้อความผลการแข่งขันไปยัง Amazon SNS
4. Amazon SNS กระจายข้อความแบบขนานไปยัง 2 คิวใน SQS พร้อมกัน:
   - คิวประวัติการแข่งขัน: นำส่งข้อมูลให้ Lambda บันทึกประวัติแมตช์ลงตาราง LorcanaMatchHistory
   - คิวสถิติผู้เล่น: นำส่งข้อมูลให้ Lambda อัปเดตยอดชนะ/แพ้ในตาราง LorcanaPlayerStats แบบป้องกันการนับซ้ำ
5. หากระบบบันทึกส่วนใดส่วนหนึ่งทำงานช้า อีกส่วนหนึ่งยังคงทำงานได้ตามปกติโดยไม่กระทบกัน

#### เส้นทางที่ 5: การเรียกดูตารางผู้นำด้วยระบบหน่วยความจำแคช
1. ผู้ใช้เปิดหน้าตารางผู้นำ
2. เบราว์เซอร์เรียกดูข้อมูลผ่านเซิร์ฟเวอร์ EC2
3. เซิร์ฟเวอร์จะตรวจสอบข้อมูลในหน่วยความจำแคช ElastiCache Valkey ก่อนเสมอ
   - หากมีข้อมูลอยู่แล้ว: ส่งข้อมูลกลับทันทีภายใน 1 มิลลิวินาที
   - หากยังไม่มีข้อมูล: ดึงข้อมูลจาก DynamoDB ตาราง LorcanaPlayerStats ส่งกลับให้ผู้ใช้ พร้อมคัดลอกลงหน่วยความจำแคชโดยกำหนดอายุข้อมูลไว้ 60 วินาที
4. หากระบบแคชหยุดทำงาน เซิร์ฟเวอร์จะสลับไปดึงข้อมูลจาก DynamoDB โดยตรงโดยที่ผู้ใช้งานไม่พบข้อผิดพลาด

## 3. การเปรียบเทียบส่วนประกอบคลาวด์กับสิ่งของในชีวิตประจำวัน

| บริการคลาวด์ | สิ่งของเปรียบเทียบในชีวิตประจำวัน | หน้าที่การทำงาน |
|---|---|---|
| **Application Load Balancer** | พนักงานต้อนรับหน้าร้าน | คอยต้อนรับลูกค้าที่เดินเข้ามาหน้าร้าน และจัดสรรลูกค้าไปยังเคาน์เตอร์บริการที่ว่าง เพื่อไม่ให้เคาน์เตอร์ใดเคาน์เตอร์หนึ่งรับลูกค้ามากเกินไป |
| **EC2 Auto Scaling Group** | จำนวนเคาน์เตอร์บริการที่เปิดปิดได้ | เมื่อลูกค้าในร้านเพิ่มขึ้นจนพนักงานบริการไม่ทัน ระบบจะเปิดเคาน์เตอร์เพิ่ม และเมื่อลูกค้าลดลงจะปิดเคาน์เตอร์ที่ไม่จำเป็นเพื่อประหยัดค่าใช้จ่าย |
| **Amazon SQS** | สายพานลำเลียงกล่องพัสดุ | เป็นที่พักกล่องงานเพื่อรอให้ช่างหยิบไปทำตามลำดับ ช่วยป้องกันไม่ให้งานล้นโต๊ะช่าง |
| **Dead Letter Queue (DLQ)** | ลังเก็บของชำรุดรอการตรวจสอบ | เมื่อกล่องพัสดุใดเปิดไม่ได้หลังจากพยายามลองเปิด 3 ครั้ง พนักงานจะแยกกล่องนั้นมาวางในลังนี้ เพื่อให้สายพานหลักเดินต่อได้โดยไม่ติดขัด |
| **Amazon SNS** | ลำโพงประกาศข่าวสารตามสาย | เมื่อผู้จัดการประกาศผลงานผ่านไมโครโฟน แผนกจัดเก็บเอกสารและแผนกบัญชีจะได้ยินเสียงประกาศพร้อมกันทันที และแยกย้ายไปบันทึกงานของตน |
| **AWS Lambda** | ช่างผู้เชี่ยวชาญเฉพาะกิจ | ช่างที่จะถูกเรียกมาเฉพาะเวลาที่มีงานเข้ามา เมื่อซ่อมงานชิ้นนั้นเสร็จก็รับค่าจ้างเฉพาะชิ้นงานแล้วกลับบ้าน ไม่ต้องนั่งรอในออฟฟิศตลอดทั้งวัน |
| **Amazon DynamoDB** | ตู้ลิ้นชักเก็บเอกสารแบบดัชนีด่วน | ตู้เก็บข้อมูลที่สามารถค้นหาเอกสารตามรหัสประจำตัวได้อย่างแม่นยำและรวดเร็ว แม้จะมีเอกสารเพิ่มขึ้นเป็นล้านแผ่น |
| **Amazon ElastiCache** | กระดานไวท์บอร์ดสรุปข้อมูลด่วน | กระดานที่จดข้อมูลสรุปยอดนิยมไว้หน้าห้องประชุม เพื่อให้ทุกคนมองเห็นตัวเลขล่าสุดได้ทันทีโดยไม่ต้องเดินไปเปิดค้นในตู้เอกสาร |

## 4. ขั้นตอนการทดสอบและสาธิตระบบ

### 4.1 การเตรียมความพร้อม
1. เปิดเบราว์เซอร์ไปที่ที่อยู่ของ Application Load Balancer
2. เตรียมหน้าต่างเบราว์เซอร์ 2 หน้าต่าง (แนะนำให้เปิดแบบหน้าต่างปกติ 1 หน้าต่าง และหน้าต่างไม่ระบุตัวตน 1 หน้าต่าง)

### 4.2 ขั้นตอนการสาธิต

1. **สร้างบัญชีผู้ใช้:**
   - หน้าต่างที่ 1: ลงทะเบียนผู้ใช้ `player1` และเข้าสู่ระบบ
   - หน้าต่างที่ 2: ลงทะเบียนผู้ใช้ `player2` และเข้าสู่ระบบ

2. **ทดสอบระบบจัดเด็คและวิเคราะห์เด็ค:**
   - เข้าเมนู Deck Builder
   - เลือกสร้างเด็คใหม่ ระบบจะโหลดข้อมูลการ์ดชุดที่ 1 ถึง 13 จากระบบแคชของเบราว์เซอร์อย่างรวดเร็ว
   - บันทึกเด็คและกดปุ่มวิเคราะห์เด็ค
   - เข้าเมนู Analytics สังเกตกราฟค่าร่าย สัดส่วนหมึก และคะแนนความเข้ากันได้ของการ์ดที่ประมวลผลจากระบบเบื้องหลัง

3. **ทดสอบการเล่นเกมออนไลน์ข้ามหน้าต่าง:**
   - หน้าต่างที่ 1: เข้าเมนู Play และกดปุ่ม Create Room จะได้รับรหัสห้อง 6 หลัก
   - หน้าต่างที่ 2: เข้าเมนู Play กรอกรหัสห้อง 6 หลักและกด Join Room
   - ทั้งสองหน้าต่างจะเข้าสู่หน้ากระดานแข่งขันทันที

4. **ทดสอบกฎกติกาและคีย์เวิร์ดของเกม:**
   - ทดสอบการนำการ์ดเข้าบ่อหมึก: สังเกตว่านำเข้าได้เฉพาะการ์ดที่มีสัญลักษณ์หมึกรอบตัวเลขค่าร่ายเท่านั้น
   - ทดสอบการลงการ์ดและการเควสต์: สังเกตตัวแสดงสถานะเทิร์นและกรอบเน้นการ์ดที่สามารถกระทำได้
   - ทดสอบคีย์เวิร์ดพิเศษ:
     - การ์ด Rush: สามารถสั่งท้าทายได้ทันทีในเทิร์นที่ลง
     - การ์ด Evasive: ไม่สามารถถูกท้าทายได้จากตัวละครทั่วไป เว้นแต่ตัวละครที่มี Evasive หรือ Alert
     - การ์ด Bodyguard: บังคับให้คู่แข่งต้องเลือกท้าทายตัวละครนี้ก่อน
     - การ์ด Ward: ไม่ปรากฏในรายการเป้าหมายให้เลือกเมื่อคู่แข่งใช้ความสามารถ

5. **ทดสอบการบันทึกประวัติการแข่งขันและตารางผู้นำ:**
   - ดำเนินการเล่นจนฝ่ายใดฝ่ายหนึ่งมีแต้มครบ 20 หรือกดยอมแพ้
   - เข้าเมนู Match History ในทั้งสองหน้าต่าง จะพบรายการแมตช์ที่เพิ่งแข่งขันจบภายในเวลาไม่เกิน 5 วินาที
   - เข้าเมนู Leaderboard จะพบสถิติการชนะของผู้เล่นอัปเดต โดยมีการตอบสนองอย่างรวดเร็วจากหน่วยความจำแคช

## 5. อภิธานศัพท์เทคนิค

- **Application Load Balancer (ALB):** อุปกรณ์กระจายภาระงานบนคลาวด์ ทำหน้าที่รับคำขอจากผู้ใช้งานผ่านอินเทอร์เน็ตและส่งต่อไปยังเครื่องเซิร์ฟเวอร์ที่เหมาะสม
- **Auto Scaling Group (ASG):** กลุ่มของเครื่องเซิร์ฟเวอร์เสมือนที่สามารถปรับเพิ่มหรือลดจำนวนเครื่องโดยอัตโนมัติตามปริมาณการใช้งานจริง
- **Availability Zone (AZ):** ศูนย์ข้อมูลคลาวด์ที่ตั้งอยู่แยกจากกันในเชิงภูมิศาสตร์และมีระบบไฟฟ้าเครือข่ายแยกอิสระ เพื่อป้องกันความเสียหายร่วม
- **Cache-Aside:** รูปแบบการบริหารจัดการหน่วยความจำแคช โดยแอปพลิเคชันจะตรวจสอบแคชก่อน หากไม่พบจึงไปอ่านจากฐานข้อมูลหลักแล้วนำมาบันทึกเก็บไว้ในแคช
- **Dead Letter Queue (DLQ):** คิวพิเศษสำหรับจัดเก็บข้อความที่ประมวลผลไม่สำเร็จตามจำนวนครั้งที่กำหนด เพื่อป้องกันข้อความสูญหายและไม่ให้กระทบการทำงานของคิวหลัก
- **Decoupling:** การออกแบบระบบให้ส่วนประกอบย่อยทำงานแยกเป็นอิสระต่อกัน เพื่อไม่ให้ความล้มเหลวของส่วนหนึ่งส่งผลกระทบต่อเนื่องไปยังส่วนอื่น
- **Fan-Out:** สถาปัตยกรรมกระจายข้อความ โดยข้อความจากจุดส่งจุดเดียวจะถูกส่งต่อไปยังผู้รับหรือคิวปลายทางหลายตัวพร้อมกันในเวลาเดียว
- **Idempotency:** คุณสมบัติการทำงานที่แม้จะได้รับคำสั่งซ้ำด้วยข้อมูลเดิมหลายครั้ง ผลลัพธ์สุดท้ายของระบบจะยังคงถูกต้องและไม่เกิดการบันทึกซ้ำซ้อน
- **JSON Web Token (JWT):** รูปแบบมาตรฐานในการส่งข้อมูลยืนยันตัวตนระหว่างผู้ใช้กับเซิร์ฟเวอร์ในรูปแบบที่มีการลงลายมือชื่อดิจิทัลกำกับ
- **Least Privilege:** หลักการกำหนดสิทธิ์ความปลอดภัยขั้นต่ำ โดยให้สิทธิ์การเข้าถึงข้อมูลและคำสั่งเฉพาะเท่าที่จำเป็นต่อการปฏิบัติงานเท่านั้น
- **Pure Function:** ฟังก์ชันการคำนวณที่ให้ผลลัพธ์เหมือนเดิมเสมอเมื่อได้รับข้อมูลนำเข้าชุดเดิม และไม่มีการเปลี่ยนแปลงสถานะหรือผลข้างเคียงภายนอก
- **Redrive Policy:** กฎเกณฑ์ที่กำหนดเงื่อนไขในการพยายามประมวลผลข้อความซ้ำ ก่อนที่จะส่งข้อความที่ล้มเหลวไปยังคิวข้อความตกค้าง
- **Single-Page Application (SPA):** เว็บแอปพลิเคชันที่โหลดหน้าเว็บหลักเพียงครั้งเดียว และใช้สคริปต์ในการปรับเปลี่ยนเนื้อหาตามการใช้งานของผู้ใช้โดยไม่ต้องโหลดหน้าใหม่ทั้งหมด
- **Valkey:** ซอฟต์แวร์ระบบจัดการฐานข้อมูลในหน่วยความจำประสิทธิภาพสูง ซึ่งรองรับคำสั่งและโครงสร้างข้อมูลแบบเดียวกับ Redis
