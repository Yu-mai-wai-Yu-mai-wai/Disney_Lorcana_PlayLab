Problem & Vision 02 / 12

ปัญหาของ Physical TCG สู่โซลูชันบนคลาวด์

การออกแบบเพื่อทลายข้อจำกัดด้านต้นทุน ความหน่วงเครือข่าย และความเสมือนจริง

⚠️ ข้อจำกัดของระบบเดิม (Pain Points)
  • ต้นทุนการ์ดจริงสูง & หาคู่ซ้อมยาก: การซื้อการ์ดจริงมีราคาสูง และผู้เล่นต่างพื้นที่หาคู่แข่งระดับใกล้เคียงกันได้ลำบาก
  • Traditional VM Server Overhead: ระบบจำลองการ์ดทั่วไปใช้ Dedicated Server รัน 24 ชม. เสียค่าใช้จ่ายคงที่ตลอดเวลาแม้ไม่มีผู้ใช้
  • Network Latency (>300ms): การใช้ HTTP Polling ทำให้การอัปเดตสถานะกระดานช้า ไม่ตอบโจทย์เกมการ์ดระดับแข่งขัน
  • UI ขาดมิติความสมจริง: ตัวจำลองทั่วไปเป็นภาพ 2D แบนราบ ขาดมิติฟิสิกส์ของการสัมผัสการ์ดจริง
🎯 วัตถุประสงค์และการแก้ปัญหาบน AWS Cloud
  • Low Latency Sub-100ms: พัฒนาระบบ Real-time Multiplayer ด้วย WebSocket ซิงค์กระดานแบบสองทิศทาง
  • Elastic Cloud Infrastructure: ออกแบบระบบที่ขยายตัวอัตโนมัติตามโหลดผู้เล่น และลดสเกลเป็นศูนย์ (Scale-to-Zero) ยามว่าง
  • Deck Builder & Rules Engine: ตรวจสอบกฎทางการ (60 ใบ, สูงสุด 2 สี, ห้ามซ้ำเกิน 4 ใบ) บนการ์ด 408 ใบ
  • Luxury Physical Experience: ถ่ายทอดความหรูหราด้วย 3D Foil Inspector, Pack Opening, และการหมุนการ์ด Ready/Exert

Architecture Evolution 04 / 12

เส้นทางการย้ายสถาปัตยกรรม (Architecture Evolution)

เหตุผลและผลลัพธ์จากการเปลี่ยนผ่าน Pure Serverless S3 สู่ Lean Multi-AZ IaaS

📦 Baseline: Pure Serverless S3 Hosting
  • Frontend: Amazon S3 Static Website Hosting
  • Backend: AWS Lambda 4 ฟังก์ชัน (Auth, Deck, Room, Analyzer)
  • API: AWS API Gateway (HTTP REST + WebSockets WSS)
  • ข้อจำกัดเชิงวิชาการ: S3 เป็นเพียง Object Storage ไม่ได้แสดงทักษะด้าน Compute Management, Custom Subnetting, Security Group Chaining หรือ Load Balancing Lifecycle
🚀 New Evolution: Lean Multi-AZ IaaS Stack
  • Custom VPC: แบ่ง Subnet 2 โซนอิสระ (`us-east-1a` & `us-east-1b`)
  • Traffic Routing: Application Load Balancer (ALB) มี Health Check `/health`
  • Elastic Compute: EC2 Auto Scaling Group (`t3.micro`) ขยาย 1 ➔ 3 เครื่อง
  • Containerization: Docker Compose (Nginx Web Proxy + Node.js 20 App)
  • ตอบโจทย์คะแนน 5%: ครบถ้วนตามเกณฑ์ Cloud & Software Engineering

Real-time Engineering 07 / 12

กลไก Real-time WebSockets & Sub-100ms Latency

การสื่อสารแบบสองทิศทาง Optimistic UI และการรับมือเหตุการณ์หลุดการเชื่อมต่อ

⚡ สถาปัตยกรรมการซิงค์ข้อมูล (Sync Flow)
  • Optimistic Rendering: เมื่อผู้เล่นลากการ์ด UI ฝั่งตนเองขยับทันที (0ms) แล้วส่ง Action ขนาดเล็ก (~120 bytes) ผ่าน WebSocket
  • Sub-100ms Relay: Server ทำหน้าที่กระจาย Action (Card Move, Exert, Ink, Lore) ให้คู่แข่งในห้องเดียวกันด้วย Latency เพียง 52–82ms
  • ห้องเล่นจับคู่ด้วย Room Code: จับคู่ 2 ผู้เล่นด้วยรหัส 6 หลัก และแยก Session ชัดเจน

🔄 Auto-Reconnect & Grace Window 30s
  • Grace Window 30 วินาที: หากผู้เล่นเน็ตหลุด เซิร์ฟเวอร์จะยังคงรักษาสถานะกระดานไว้ ไม่ตัดจบเกมทันที

Database & NoSQL 08 / 12

การออกแบบ NoSQL Schema & DynamoDB TTL Pattern

การจัดโครงสร้างตารางข้อมูลเพื่อประสิทธิภาพความเร็ว $O(1)$ และการล้างข้อมูลอัตโนมัติไร้ต้นทุน

👤 UsersTable
  • Partition Key: `userId` (String / UUID)
  • Attributes: `username`, `email`, `passwordHash`, `createdAt`
  • ความปลอดภัย: รหัสผ่านแฮชด้วย bcrypt 10 salt rounds ไม่มีการเก็บรหัสผ่านจริง
📚 DecksTable
  • Partition Key: `userId` (String)
  • Sort Key: `deckId` (String)
  • Attributes: `deckName`, `inks` (List), `cards` (JSON Map), `updatedAt`
  • ดึงเด็คทั้งหมดของ User คนเดียวได้ใน 1 Query
⏱️ RoomStateTable (TTL)
  • Partition Key: `roomId` (String)
  • Sort Key: `connectionId` (String)
  • Time-To-Live (TTL): ตั้งหมดอายุใน 2 ชั่วโมง หลังสร้างห้อง
  • Zero Cost Deletion: DynamoDB ลบข้อมูลขยะทิ้งเองเบื้องหลัง ไม่เสียค่า Write Units
Security & DevOps 09 / 12

ความมั่นคงปลอดภัย & การแก้โจทย์ AWS Learner Lab

การก้าวข้ามข้อจำกัด Sandbox ด้วยวิศวกรรมซอฟต์แวร์และการรักษาความปลอดภัยระดับ OWASP

🛠️ การแก้ข้อจำกัด AWS Learner Lab Sandbox
  • บล็อกสิทธิ์ `iam:CreateRole`: สภาพแวดล้อมแล็บไม่อนุญาตให้สร้าง IAM Role ใหม่ เราแก้ปัญหาด้วยการผูก `LabRole` ที่มีอยู่แล้วผ่าน IMDSv2
  • Session Token หมดอายุใน 4 ชม.: พัฒนาระบบสคริปต์กึ่งอัตโนมัติ และแยก Environment ตัวแปร `.env` ออกจากโค้ดจริง
  • Payload Format Version 1.0 Mismatch: แก้ปัญหา API Gateway 405 Method Not Allowed โดยบังคับใช้ Integration Version 1.0 รับส่ง Header และ Method ครบถ้วน
🔒 OWASP Security Hardening
  • A01 Broken Access Control: ตรวจสอบสิทธิ์เจ้าของเด็คผ่าน JWT Claims ทุกครั้งที่ทำการแก้ไข/ลบ
  • A02 Cryptographic Failures: ใช้ bcrypt Cost 10 สำหรับ Password และบังคับ HTTPS/WSS ตลอดเส้นทาง
  • A07 Authentication Flaws: ติดตั้ง In-Memory Rate Limiter ดักจับการพยายาม Brute-force Login (บล็อกหลังผิดเกิน 5 ครั้ง)
  • IMDSv2 Enforcement: กำหนด Token Hop Limit = 1 เพื่อป้องกัน SSRF จาก EC2 Metadata Service
