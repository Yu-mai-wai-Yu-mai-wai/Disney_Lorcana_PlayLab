# ร่างอีเมลขอคำปรึกษาและข้อเสนอแนะสถาปัตยกรรมคลาวด์
**วิชา:** Cloud Computing  
**โครงงาน:** Disney Lorcana PlayLab Cloud  
**ผู้จัดทำ:** นายตะวัน [รหัสนักศึกษา] และทีมโครงงาน  

---

**หัวข้ออีเมล:** ขอคำปรึกษาและข้อเสนอแนะในการปรับปรุงสถาปัตยกรรมคลาวด์ โครงงาน Disney Lorcana PlayLab Cloud

เรียน อาจารย์ประจำวิชา Cloud Computing ที่เคารพ

กระผมนายตะวัน [รหัสนักศึกษา] ตัวแทนกลุ่มโครงงานระบบ Disney Lorcana PlayLab Cloud มีความประสงค์ขอคำปรึกษาและข้อเสนอแนะจากอาจารย์เกี่ยวกับการออกแบบสถาปัตยกรรมคลาวด์บน AWS ของโครงงาน เพื่อนำมาปรับปรุงระบบให้มีความสมบูรณ์ ถูกต้องตามหลัก Cloud Architecture ที่ดี และสอดคล้องกับเกณฑ์การประเมิน ก่อนการส่งมอบงานและนำเสนอฉบับสมบูรณ์ครับ

### 1. ภาพรวมสถาปัตยกรรมของระบบในปัจจุบัน
ระบบ Disney Lorcana PlayLab Cloud เป็นเว็บแอปพลิเคชันการ์ดเกมออนไลน์ที่มีผู้เล่น 2 คนแข่งขันกันแบบเรียลไทม์ พร้อมระบบจัดเด็คและบันทึกสถิติ โดยในปัจจุบันทางกลุ่มได้วางโครงสร้างระบบบน AWS (Region: us-east-1) ดังนี้:

1. **Web & API Tier:**
   - ใช้ Application Load Balancer กระจายโหลดไปยัง EC2 Auto Scaling Group (t3.micro จำนวน 2-4 เครื่อง) แบบ Multi-AZ (us-east-1a และ us-east-1b)
   - Nginx ทำหน้าที่ Reverse Proxy และแคชไฟล์ข้อมูลการ์ดขนาดใหญ่ (บีบอัด Gzip จาก 2.35 MB เหลือ 436 KB พร้อม Cache-Control Immutable 1 ปี)
2. **Real-time Tier:**
   - แยกการเล่นเกมแบบสองทางออกจาก HTTP ปกติ โดยใช้ Amazon API Gateway WebSocket API ทำงานร่วมกับ AWS Lambda (lorcana-room) และบันทึกสถานะห้องลง DynamoDB ช่วยป้องกันปัญหาการผูกมัด Connection บนเซิร์ฟเวอร์หลัก
3. **Asynchronous Deck Analysis:**
   - ใช้ Amazon SQS ร่วมกับ Dead Letter Queue (DLQ) สำหรับพักคิวงานวิเคราะห์เด็ค และให้ AWS Lambda ดึงไปคำนวณกราฟค่าร่ายและคะแนนความสอดคล้องของการ์ดก่อนบันทึกลง DynamoDB
4. **Decoupled Match Event (Fan-Out):**
   - เมื่อจบเกม คำขอ POST /api/matches จะส่ง Event เข้า Amazon SNS Topic แล้วกระจายข้อมูลแบบ Fan-Out ไปยัง SQS 2 คิวคู่ขนาน เพื่อให้ Lambda แยกบันทึกประวัติแมตช์ (LorcanaMatchHistory) และคำนวณสถิติผู้เล่น (LorcanaPlayerStats) แบบ Idempotent
5. **Caching & Persistence Tier:**
   - ใช้ Amazon DynamoDB (On-Demand) เป็นฐานข้อมูลหลัก
   - ใช้ Amazon ElastiCache Valkey ทำงานแบบ Cache-Aside ให้กับตารางผู้นำ (Leaderboard) ช่วยลดเวลาตอบสนองจาก 41 มิลลิวินาที เหลือ 1 มิลลิวินาที

*(ทางกลุ่มได้แนบไฟล์แผนภาพสถาปัตยกรรมระบบ aws_architecture_lorcana_playlab.drawio มาพร้อมกับอีเมลฉบับนี้ด้วยแล้วครับ)*

### 2. ประเด็นที่ขอรับคำปรึกษาและข้อเสนอแนะจากอาจารย์
ทางกลุ่มได้รวบรวมข้อสงสัยเชิงวิศวกรรมสถาปัตยกรรมที่ต้องการให้อาจารย์ช่วยชี้แนะเป็น 4 ประเด็นหลัก ดังนี้ครับ:

1. **ประเด็นเรื่องเครือข่ายและความปลอดภัย (VPC & Subnet Isolation):**
   ปัจจุบันเนื่องจากข้อจำกัดด้านงบประมาณของ AWS Academy Learner Lab ทางกลุ่มจึงไม่ได้เปิดใช้ NAT Gateway และวาง EC2 ไว้ใน Public Subnet โดยควบคุมความปลอดภัยผ่าน Security Group อย่างเข้มงวด
   - *คำถาม:* หากประเมินตามมาตรฐาน Production จริง อาจารย์มองว่าควรปรับเป็น Private Subnet แล้วใช้ VPC Endpoints (Gateway Endpoint สำหรับ DynamoDB และ Interface Endpoints สำหรับ SQS/SNS) หรือควรคงแนวทางเดิมโดยระบุเหตุผลเรื่อง Trade-off ด้านต้นทุนของงบประมาณแล็บในรายงานครับ?

2. **ประเด็นการเลือกใช้ EC2 ASG เทียบกับ Container หรือ Serverless ทั้งระบบ:**
   ปัจจุบันทางกลุ่มเลือกใช้ EC2 ASG + ALB ในส่วน Web API เพื่อแสดงให้เห็นการจัดการเครื่องเซิร์ฟเวอร์เสมือน การตั้งค่า Load Balancer และการปรับขนาดอัตโนมัติ
   - *คำถาม:* ในมุมมองของอาจารย์ การที่ระบบมีทั้งส่วน EC2 ASG และส่วน Serverless (Lambda + SQS + SNS) ผสมผสานกัน ถือว่ามีความเหมาะสมและครอบคลุมขอบเขตวิชาแล้วหรือไม่ หรือมีข้อเสนอแนะว่าควรปรับส่วน Web Tier ไปเป็น ECS Fargate หรือ Serverless ล้วนเพื่อให้ระบบมีความทันสมัยมากขึ้นครับ?

3. **ประเด็นความเหมาะสมและความซับซ้อนของส่วนประกอบระบบ (ElastiCache):**
   ในการทดสอบ ระบบสามารถอ่านข้อมูล Leaderboard จาก ElastiCache Valkey ได้เร็ว 1 มิลลิวินาที (เทียบกับ DynamoDB ที่ 41 มิลลิวินาที)
   - *คำถาม:* ด้วยขนาดของข้อมูลผู้เล่นในระดับโครงงานนักศึกษา การคง ElastiCache ไว้ถือเป็นจุดเด่นที่ช่วยแสดงความเข้าใจเรื่อง Caching Layer หรืออาจารย์มองว่าเป็นการเพิ่มความซับซ้อนและต้นทุนเกินความจำเป็นที่ควรตัดออกหรือไม่ครับ?

4. **ประเด็นการกระจายข้อมูล (SNS Fan-Out เทียบกับ EventBridge):**
   ปัจจุบันทางกลุ่มเลือกใช้ SNS Fan-Out สู่ SQS 2 คิว หากต้องการปรับปรุงให้รองรับเงื่อนไขการกรองข้อมูลที่ซับซ้อนในอนาคต อาจารย์มองว่าควรศึกษาการย้ายไปใช้ Amazon EventBridge หรือไม่ครับ?

ทางกลุ่มพร้อมรับฟังทุกข้อแนะนำเพื่อนำไปปรับปรุงโค้ด สถาปัตยกรรม และเอกสารรายงานฉบับสมบูรณ์ให้ถูกต้องและมีคุณภาพสูงสุดครับ
